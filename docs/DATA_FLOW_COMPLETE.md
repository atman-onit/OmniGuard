# Complete Data Flow & Property Lifecycle

## Overview
This document traces a single incident from video frame to dashboard alert, showing exactly what properties are created/modified at each step and why.

---

## STAGE 1: PERCEPTION MODULE - DETECTION & TRACKING

### Input
```
Raw video frame (640x480 pixels)
└─ contains: people, bags, restricted zones, etc
```

### Step 1.1: YOLO Detection
**What happens:** Frame fed to pretrained YOLO model → produces detections

**Output properties created:**
```python
detection = {
    "class": "person",              # YOLO output: what object is this?
    "confidence": 0.89,             # YOLO output: 0-1 certainty
    "box": (x1, y1, x2, y2)        # YOLO output: bounding box pixels
}
```

**Example for a single frame with 3 people:**
```python
raw_detections = [
    {"class": "person", "confidence": 0.87, "box": (48, 398, 245, 902)},
    {"class": "person", "confidence": 0.85, "box": (221, 405, 344, 857)},
    {"class": "person", "confidence": 0.83, "box": (669, 392, 809, 877)},
]
```

### Step 1.2: Centroid Tracking
**What happens:** Match detections to previous frame's tracked objects by center-point distance

**Input:** `raw_detections` from step 1.1

**Output properties created/added:**
```python
tracked_object = {
    "class": "person",                    # from detection
    "confidence": 0.87,                   # from detection
    "box": (48, 398, 245, 902),          # from detection
    
    "track_id": 5,                        # NEW: assigned by tracker
    "dwell_time_seconds": 12.3            # NEW: accumulated by tracker
}
```

**Why track_id matters:** Without it, each frame's detection looks like a different object. With it, you can ask "has this bag been sitting here for 30 seconds?"

**Example for one frame:**
```python
tracked_objects = [
    {"class": "person", "confidence": 0.87, "box": (48, 398, 245, 902), "track_id": 1, "dwell_time_seconds": 0},
    {"class": "person", "confidence": 0.85, "box": (221, 405, 344, 857), "track_id": 2, "dwell_time_seconds": 0},
    {"class": "person", "confidence": 0.83, "box": (669, 392, 809, 877), "track_id": 3, "dwell_time_seconds": 0},
    {"class": "backpack", "confidence": 0.79, "box": (400, 350, 430, 400), "track_id": 4, "dwell_time_seconds": 38.5}
]
```

### Step 1.3: Occupancy Tracking
**What happens:** Count persons per zone, calculate occupancy %

**Input:** `tracked_objects` from step 1.2

**Output properties created:**
```python
zone_occupancy = {
    "zone": "Gate_3",                     # which zone?
    "current_count": 2,                   # how many people in zone?
    "capacity": 10,                       # max safe occupancy
    "occupancy_percentage": 20.0,         # count / capacity * 100
    "trend": "stable",                    # increasing/stable/decreasing
    "timestamp": "2026-08-19T14:35:22Z"  # when was this measured?
}
```

**Action:** If `occupancy_send_counter >= OCCUPANCY_SEND_INTERVAL`, send this to backend

```python
POST http://localhost:8000/zones/occupancy
{
    "zone": "Gate_3",
    "current_count": 2,
    "capacity": 10,
    "occupancy_percentage": 20.0,
    "trend": "stable",
    "timestamp": "2026-08-19T14:35:22Z"
}
```

## STAGE 2: PERCEPTION MODULE - RULE CHECKING

### Input
`tracked_objects` from step 1.2

### Step 2.1: Check Crowd Rule
**Logic:** If person count in zone >= CROWD_THRESHOLD → fire alert

**Example:** Zone has 8 people, threshold is 5 → FIRE

**Output incident created:**
```python
incident = {
    "incident_id": "inc_a1b2c3d4",        # generated by perception
    "type": "overcrowding",               # which rule fired?
    "zone": "Gate_3",                     # where did it happen?
    "timestamp": "2026-08-19T14:35:22Z", # when?
    "count": 8,                           # person count in zone
    
    # Optional fields left null
    "tracked_object_id": None,
    "dwell_time_seconds": None,
    "detection_confidence": None
}
```

**Action:** POST to backend

```python
POST http://localhost:8000/incidents
{
    "incident_id": "inc_a1b2c3d4",
    "type": "overcrowding",
    "zone": "Gate_3",
    "timestamp": "2026-08-19T14:35:22Z",
    "count": 8,
    "tracked_object_id": None,
    "dwell_time_seconds": None,
    "detection_confidence": None
}
```

### Step 2.2: Check Baggage Rule
**Logic:** If bag stationary for N seconds with no person nearby → fire alert

**Example:** Backpack (track_id=4) dwell_time=38.5s >= 30s threshold + no one within 100px → FIRE

**Output incident created:**
```python
incident = {
    "incident_id": "inc_x9y8z7w6",        # generated by perception
    "type": "unattended_baggage",         # which rule fired?
    "zone": None,                         # baggage rule doesn't use zone
    "timestamp": "2026-08-19T14:35:22Z",
    "tracked_object_id": 4,               # which object?
    "dwell_time_seconds": 38.5,           # how long stationary?
    "detection_confidence": 0.79,         # YOLO confidence for baggage
    
    # Field not used
    "count": None
}
```

### Step 2.3: Check Intrusion Rule
**Logic:** If person detected inside restricted zone → fire alert

**Example:** Person (track_id=5) center point inside Restricted_Lab polygon → FIRE

**Output incident created:**
```python
incident = {
    "incident_id": "inc_p8q7r6s5",
    "type": "intrusion",
    "zone": "Restricted_Lab",
    "timestamp": "2026-08-19T14:35:22Z",
    "tracked_object_id": 5,
    "detection_confidence": 0.92,
    
    # Fields not used
    "dwell_time_seconds": None,
    "count": None
}
```

### Step 2.4: Check Fire Rule
**Logic:** If fire/smoke classifier confidence > threshold → fire alert

**Output incident created:**
```python
incident = {
    "incident_id": "inc_m1n2o3p4",
    "type": "fire",
    "zone": "Building_A_Floor_2",
    "timestamp": "2026-08-19T14:35:22Z",
    "detection_confidence": 0.87,
    
    # Fields not used
    "tracked_object_id": None,
    "dwell_time_seconds": None,
    "count": None
}
```

## STAGE 3: BACKEND - INGESTION & PERSISTENCE

### Input
The incident JSON from perception (IncidentIn)

### Step 3.1: Backend receives POST /incidents
**Endpoint:** `POST /incidents`

**Request body (from perception):**
```json
{
    "incident_id": "inc_a1b2c3d4",
    "type": "overcrowding",
    "zone": "Gate_3",
    "timestamp": "2026-08-19T14:35:22Z",
    "count": 8,
    "tracked_object_id": null,
    "dwell_time_seconds": null,
    "detection_confidence": null
}
```

### Step 3.2: Save to Database Immediately
**What happens:** Incident saved to DB *before* agent is called (fail-safe)

**Backend adds these properties automatically:**
```python
incident_in_db = {
    # From perception (unchanged)
    "incident_id": "inc_a1b2c3d4",
    "type": "overcrowding",
    "zone": "Gate_3",
    "timestamp": "2026-08-19T14:35:22Z",
    "count": 8,
    "tracked_object_id": None,
    "dwell_time_seconds": None,
    "detection_confidence": None,
    
    # Backend auto-adds these
    "id": 1,                                    # DB primary key
    "created_at": "2026-08-19T14:35:22.123Z",  # when saved
    "updated_at": "2026-08-19T14:35:22.123Z",  # same as created_at on insert
    "status": "new",                            # incident state
    
    # Agent will fill these (empty now)
    "severity": None,
    "reasoning_summary": None,
    "correlated_incident_ids": None,
    "recommended_action": None,
    "notification_draft": None,
    
    # Human operator will fill these (empty now)
    "acknowledged_at": None,
    "acknowledged_by": None
}
```

**DB write happens instantly** — incident is now in the database, safe from loss even if next steps fail.

### Step 3.3: Broadcast "incident received" to dashboard
**Via WebSocket to all connected clients:**
```json
{
    "type": "incident",
    "data": {
        "incident_id": "inc_a1b2c3d4",
        "type": "overcrowding",
        "zone": "Gate_3",
        "timestamp": "2026-08-19T14:35:22Z",
        "count": 8,
        "severity": null,           // agent hasn't run yet
        "status": "new"
    }
}
```

Dashboard sees it on alert list (but severity column is blank, showing as low priority until agent scores it)

## STAGE 4: BACKEND - AGENT PROCESSING

### Input
The incident from DB (with all fields)

### Step 4.1: Agent receives incident
**Query recent incidents from DB** (to look for correlations)

**Context the agent receives:**
```python
context = {
    "incident": {
        "incident_id": "inc_a1b2c3d4",
        "type": "overcrowding",
        "zone": "Gate_3",
        "timestamp": "2026-08-19T14:35:22Z",
        "count": 8,
        "detection_confidence": None
    },
    "recent_incidents": [
        # Look back 10 minutes for related events
        {
            "incident_id": "inc_a1b2c2d0",
            "type": "baggage",
            "zone": "Gate_3",
            "timestamp": "2026-08-19T14:33:00Z"
        }
    ]
}
```

### Step 4.2: Agent calls LLM with tool-use
**System prompt:**
```
You are a campus safety triage agent. You receive structured incident data 
from a computer vision system. Assign severity, note related incidents, 
and draft an alert message. Never invent facts.
```

**Tools agent can call:**
- `get_recent_incidents(zone, minutes)` — fetch related events
- `get_object_track_history(track_id)` — fetch object movement history
- `get_zone_context(zone)` — get zone metadata (capacity, authorization rules, etc)

**Agent reasons:**
```
Incident: Gate_3 overcrowding with 8/10 people
Recent incident: Unattended bag at same gate 2 min ago
Correlation: Possible distraction event or event attracting crowds

Decision: Escalate to HIGH severity due to correlation with baggage alert
          Gate should be monitored for crowd control
```

### Step 4.3: Agent produces output
**Output (AgentOutput schema):**
```python
agent_output = {
    "severity": "high",                    # critical/high/medium/low
    "reasoning_summary": "Gate_3 overcrowding (8/10 capacity) + recent baggage alert suggests potential event. Recommend crowd monitoring.",
    "correlated_incident_ids": ["inc_a1b2c2d0"],  # linked incidents
    "recommended_action": "dispatch_security",    # what to do
    "notification_draft": "Gate 3 approaching capacity (80%) with recent security alert — dispatch patrol"
}
```

### Step 4.4: Backend updates incident in DB
**Update the incident row with agent output:**
```python
incident_after_agent = {
    # Original fields (unchanged)
    "incident_id": "inc_a1b2c3d4",
    "type": "overcrowding",
    "zone": "Gate_3",
    "timestamp": "2026-08-19T14:35:22Z",
    "count": 8,
    "detected_confidence": None,
    
    # Still unchanged
    "id": 1,
    "created_at": "2026-08-19T14:35:22.123Z",
    "updated_at": "2026-08-19T14:35:22.456Z",  # updated now
    "status": "new",
    
    # NOW FILLED BY AGENT
    "severity": "high",
    "reasoning_summary": "Gate_3 overcrowding (8/10 capacity) + recent baggage alert suggests potential event. Recommend crowd monitoring.",
    "correlated_incident_ids": ["inc_a1b2c2d0"],
    "recommended_action": "dispatch_security",
    "notification_draft": "Gate 3 approaching capacity (80%) with recent security alert — dispatch patrol",
    
    # Still empty (waiting for operator)
    "acknowledged_at": None,
    "acknowledged_by": None
}
```

### Step 4.5: Broadcast enriched incident to dashboard
**Via WebSocket:**
```json
{
    "type": "incident_enriched",
    "data": {
        "incident_id": "inc_a1b2c3d4",
        "type": "overcrowding",
        "zone": "Gate_3",
        "timestamp": "2026-08-19T14:35:22Z",
        "count": 8,
        "severity": "high",           // NOW POPULATED
        "reasoning_summary": "Gate_3 overcrowding (8/10 capacity) + recent baggage alert suggests potential event...",
        "correlated_incident_ids": ["inc_a1b2c2d0"],
        "recommended_action": "dispatch_security",
        "notification_draft": "Gate 3 approaching capacity (80%) with recent security alert — dispatch patrol",
        "status": "new"
    }
}
```

Dashboard alert list updates:
- Alert moves to top (high severity = red color)
- "Why flagged?" button now shows reasoning
- Operator can see it was correlated with another incident

## SEVERITY SCORING LOGIC (inside agent)

The agent doesn't use a formula — it uses LLM reasoning, but bounded by:

```python
DETERMINISTIC_FALLBACK = {
    "fire": "critical",           # any fire = highest urgency
    "intrusion": "high",          # unauthorized access = urgent
    "unattended_baggage": "medium",  # could be left by owner
    "overcrowding": "medium",     # common, not immediately dangerous
}
```

### Agent reasoning examples:

**Scenario 1: Fire**
```
Input: type="fire", confidence=0.87
Agent: "High confidence fire detection = immediate evacuation risk"
Output: severity="critical"
```

**Scenario 2: Overcrowding alone**
```
Input: type="overcrowding", count=8, capacity=10
Agent: "80% capacity, no other incidents"
Output: severity="medium"
```

**Scenario 3: Overcrowding + recent baggage alert**
```
Input: type="overcrowding", count=8, capacity=10
       recent_incidents=[{type="unattended_baggage", zone="Gate_3"}]
Agent: "Overcrowding + security item = possible distraction. Could indicate organized event or threat."
Output: severity="high"  # escalated due to correlation
```

**Scenario 4: Intrusion into restricted lab**
```
Input: type="intrusion", zone="Restricted_Lab", tracked_object_id=5
Agent: "Unauthorized access to restricted area. Could be academic misconduct or safety violation."
Output: severity="high"
```

## KEY DESIGN PRINCIPLES

1. **Immutable ground truth** — Perception data never changes (8 fields stay locked)
2. **Add, don't replace** — Agent adds reasoning on top, doesn't overwrite perception
3. **Fail-safe saves** — Incident saved to DB before agent even runs
4. **Explicit audit trail** — Every timestamp and actor is logged (created_at, acknowledged_by, etc)
5. **Human override capable** — Operator can change severity or mark false positive
6. **Separate concerns** — Incidents (alerts) ≠ Occupancy (state) — different data streams
